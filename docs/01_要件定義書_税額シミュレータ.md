## 1. 背景と課題

### 1.1 現状の課題

一般的なふるさと納税シミュレータ（ポータルサイト提供のもの）は、以下の前提で作られている。

- 年収が年間を通じて安定している
- 所得控除は社会保険料控除と基礎控除程度
- 税額控除（住宅ローン控除）がない、または「影響しない」と単純化している

利用者の状況はこの前提から大きく外れており、既存ツールの数値をそのまま信用できない。

### 1.2 利用者固有の複雑性

| # | 状況 | ふるさと納税上限への影響 |
|---|---|---|
| A | 2025年7月〜2026年1月の育児休業 | 2025年は約6ヶ月分、2026年は約11ヶ月分の給与収入。**育児休業給付金は非課税**のため所得に算入されない。年収ベースの簡易シミュレータは全く使えない |
| B | 育休中の社会保険料免除 | 社会保険料控除が減る → 課税所得が相対的に増える方向に働く（減収効果と逆方向） |
| C | 住宅ローン控除（0.7%・13年・2023年入居） | 所得が下がると**所得税額を住宅ローン控除が食い潰す**。控除しきれない分は住民税に繰り越されるが上限（課税総所得等×5%、最大97,500円）があり、超過分は切り捨て |
| D | 医療費控除（2025年分申請済み） | 所得が下がると足切り額が `min(10万円, 総所得金額等×5%)` の後者側に振れ、**控除額が増える**。さらに医療費控除により確定申告が必須 → **ワンストップ特例が使えない** |
| E | 生命保険料控除 | 所得税と住民税で控除額の計算が異なる（所得税は最大12万円、住民税は最大7万円） |
| F | C＋Dの複合 | 確定申告方式では寄附金控除（所得控除）が課税所得を下げ、所得税額を減らす → 住宅ローン控除の所得税での使用枠が余り、住民税側の上限に阻まれて**控除が切り捨てられる**リスクがある |

### 1.3 特に注意すべき論点

**「上限額の計算式に住宅ローン控除は影響しない」という説明は、半分しか正しくない。**

- ふるさと納税の特例分控除の上限は「住民税所得割額の20%」であり、この所得割額は**調整控除後・住宅ローン控除適用前**の額を用いる。この意味では影響しない。
- しかし「自己負担が2,000円で収まるか」という実質面では影響する。所得税額が住宅ローン控除により既にゼロ（またはごく僅か）になっている場合、寄附金控除（所得控除）による所得税の軽減が発生せず、**その分が丸ごと自己負担増**になる。
- 情報源によって説明が食い違っており、これ自体が「自分で計算する」十分な動機になる。

→ **本アプリは、公式（近似式）に頼らず、実際の税額を寄附あり／なしで二重に計算し、その差分から自己負担額を求める方式を採る**（詳細は仕様書 §4）。

## 2. 目的とゴール

### 2.1 目的

複数の控除が相互作用する状況下でも、**自己負担2,000円で収まるふるさと納税額の上限を、根拠を追える形で算出する**。

### 2.2 達成目標（KGI/KPI）

| 目標 | 指標 |
|---|---|
| G1 | 上限額を算出でき、その内訳（所得税軽減・住民税基本分・住民税特例分・自己負担）を円単位で提示できる |
| G2 | 前年の源泉徴収票・住民税決定通知書の実績値を入力した検算モードで、実額との誤差が ±1% 以内 |
| G3 | 収入見込みの不確実性に対し、安全率を設定した「推奨寄附額」を提示できる |
| G4 | 住宅ローン控除の切り捨て損失を検知し、警告を表示できる |

### 2.3 非目標（やらないこと）

- 確定申告書そのものの作成・e-Tax連携
- 税務相談・税理士業務の代替（**本アプリの出力は概算であり、最終判断は税務署／税理士に確認する前提**）
- 事業所得、不動産所得、株式譲渡損益、外国税額控除などの取り扱い（将来拡張余地としてのみ考慮）
- **サーバーサイドのユーザー認証・アカウント管理**（静的配信のため技術的に不可能。§2.4 参照）
- **クラウド同期・デバイス間の自動同期**（同期はエクスポートしたJSONファイルの手動受け渡しで代替する）

### 2.4 「複数ユーザー対応」の定義

本アプリにおける複数ユーザー対応は、次の2つを指す。**サーバー上でユーザーを識別・認証することではない。**

| 種別 | 内容 | 実現方法 |
|---|---|---|
| **U-1 マルチテナント（利用者間）** | GitHub Pages に公開したアプリを、不特定多数がそれぞれ利用できる | 全データがブラウザのオリジン別ストレージに閉じるため、**追加実装なしで自動的に分離される**。利用者Aのデータが利用者Bに見えることは原理的にない |
| **U-2 マルチプロファイル（同一ブラウザ内）** | 同じブラウザで、世帯内の複数メンバー（本人・配偶者など）のデータを切り替えて管理する | アプリ内に「人物（Person）」レイヤーを設け、人物ごとに年度プロファイルを保持する。**本要件定義で新規に追加する機能** |

U-2 が実務上の価値を持つ理由: 配偶者控除・配偶者特別控除の判定には配偶者の合計所得金額が必要であり、世帯内の2人分を同一アプリで管理できれば入力の二重化を防げる。また「世帯としてふるさと納税をいくらまでできるか」は、それぞれの上限額の合計になる。

**重要な制約**: 静的配信・クライアントサイド保存である以上、同一ブラウザを共有する人物間に**真のアクセス制御は存在しない**。パスフレーズによる保存データの暗号化（FR-27）は端末紛失時や共有PCでの偶発的な閲覧に対する緩和策であり、意図的な解析に対する防御ではない。この点は利用者に明示する。

## 3. スコープ

### 3.1 対象範囲

| 区分 | 対象 |
|---|---|
| 所得 | 給与所得（複数支払者に対応）、賞与 |
| 非課税収入 | 育児休業給付金、出産手当金、通勤手当（所得に算入しないが可視化はする） |
| 所得控除 | 基礎控除、社会保険料控除、生命保険料控除、地震保険料控除、医療費控除（セルフメディケーション税制含む）、配偶者（特別）控除、扶養控除、小規模企業共済等掛金控除（iDeCo）、寄附金控除 |
| 税額控除 | 住宅借入金等特別控除（所得税・住民税）、調整控除、寄附金税額控除（基本分・特例分） |
| 税目 | 所得税、復興特別所得税、個人住民税（所得割・均等割・森林環境税） |
| 期間 | 年単位。月次按分による年収見込み推定を含む |
| 管理単位 | 人物（Person）× 年分（Year）の2階層。1ブラウザ内に複数人物を保持可能 |

### 3.2 対象外

- 所得税の予定納税、住民税の徴収方法（特別徴収／普通徴収）の最適化
- 社会保険料そのものの精密計算（標準報酬月額テーブルからの厳密算出は任意項目とし、既定は実績入力）

## 4. 用語定義

| 用語 | 定義 |
|---|---|
| 寄附年 | ふるさと納税を実行した年（暦年）。控除は「寄附年分の所得税」と「翌年度の住民税」から行われる |
| 上限額（控除上限額） | 自己負担が2,000円で収まる寄附額の最大値 |
| 所得割額 | 住民税のうち所得に比例する部分。特例分20%枠の判定基準となるのは**調整控除後・住宅ローン控除等の税額控除前**の額 |
| 限界税率 | 課税総所得金額に対応する所得税の適用税率（5%〜45%） |
| 繰越住宅ローン控除 | 所得税から控除しきれず住民税所得割から控除される額。`min(控除残額, 課税総所得金額等×5%, 97,500円)` |
| 切り捨て損失 | 住宅ローン控除のうち、所得税でも住民税でも使い切れずに消滅した額 |

## 5. 業務要件（計算ドメイン）

### 5.1 年度をまたぐ関係の整理

利用者が混同しやすいポイントを、アプリ上で明示的に図示する。

```
2025年(令和7年)の所得
  ├→ 2025年分 所得税        （年末調整＋確定申告で精算済み）
  └→ 2026年度 住民税        （2026年6月〜2027年5月に納付）… 育休で減収 → 安い

2026年(令和8年)の所得
  ├→ 2026年分 所得税        ← 2026年に行った寄附の所得税分はここから控除
  └→ 2027年度 住民税        ← 2026年に行った寄附の住民税分はここから控除
```

**重要**: 「今年（2026年）のふるさと納税上限」は、**2026年の所得**で決まる。2026年6月に届いた住民税決定通知書（＝2025年の育休で減った所得ベース）の所得割額をそのまま使うと、上限を**大幅に過小評価**する。ここが本件で最も間違えやすい箇所であり、アプリの主要な価値である。

### 5.2 計算の基本フロー

```
給与収入（月次合計＋賞与）
  ↓ 給与所得控除
給与所得 ＝ 合計所得金額
  ↓ 所得控除の合計（基礎・社保・生保・医療費・配偶者・寄附金…）
課税総所得金額（1,000円未満切捨）
  ↓ 超過累進税率
算出所得税額
  ↓ 住宅ローン控除（税額控除）
差引所得税額（下限0）
  ↓ ×2.1%
復興特別所得税

住民税：所得控除額が所得税と異なる → 課税総所得金額（住民税）
  ↓ ×10%（標準。自治体の超過課税を反映可）
所得割（調整控除前）
  ↓ 調整控除
【所得割額】← ふるさと納税 特例分20%枠の基準
  ↓ 寄附金税額控除（基本分＋特例分）
  ↓ 住宅ローン控除（住民税分、上限あり）
所得割（納付額、100円未満切捨）＋ 均等割 ＋ 森林環境税
```

### 5.3 ふるさと納税の控除内訳

| 区分 | 計算式 |
|---|---|
| 所得税分 | `(寄附額 − 2,000) × 所得税率 × 1.021`（総所得金額等の40%が上限） |
| 住民税 基本分 | `(寄附額 − 2,000) × 10%`（総所得金額等の30%が上限） |
| 住民税 特例分 | `(寄附額 − 2,000) × (90% − 所得税率 × 1.021)`、ただし**所得割額の20%が上限** |

参考（近似式）: `上限額 ≒ 所得割額 × 20% ÷ (90% − 所得税率 × 1.021) + 2,000`

本アプリはこの近似式を**参考値としてのみ表示**し、正式な上限は差分シミュレーション方式で求める。

## 6. 機能要件

### 6.1 優先度定義
- **Must**: 初回リリースに必須
- **Should**: 課題解決の質を高める
- **Could**: 将来拡張

| ID | 機能 | 内容 | 優先度 |
|---|---|---|---|
| FR-01 | 年度プロファイル管理 | 年分（2025/2026/…）ごとに入力データを保持・切替。前年からのコピー機能 | Must |
| FR-02 | 月次収入入力 | 1〜12月の給与・賞与・社会保険料を月単位で入力。育休期間を指定すると該当月を自動で0円・社保免除に設定 | Must |
| FR-03 | 収入見込み推定 | 実績月（例: 1〜6月）＋見込み月から年収を推定。復職月・賞与額の変更をパラメータ化 | Must |
| FR-04 | 非課税所得の分離管理 | 育児休業給付金・出産手当金を「受給しているが課税所得に含めない」ものとして入力・表示。手取り把握には使うが税計算には使わない | Must |
| FR-05 | 所得控除入力 | 社会保険料・生命保険料（新旧×一般/介護医療/個人年金）・地震保険料・医療費・配偶者/扶養・iDeCo | Must |
| FR-06 | 医療費控除計算 | 支払額・補填金額から控除額を自動算出。足切り額が `総所得金額等×5%` に切り替わる場合を明示。セルフメディケーション税制との有利判定 | Must |
| FR-07 | 住宅ローン控除計算 | 年末残高・借入限度額・控除率・入居年から控除額を算出。所得税→住民税の振り分けと**切り捨て損失を可視化** | Must |
| FR-08 | 所得税額計算 | 累進税率・復興特別所得税・端数処理を含む | Must |
| FR-09 | 住民税額計算 | 所得税と異なる所得控除額、調整控除、所得割・均等割・森林環境税。自治体の超過課税率をパラメータ化（例: 神奈川県の県民税所得割 4.025%） | Must |
| FR-10 | **ふるさと納税上限額算出** | 差分シミュレーション＋二分探索により、自己負担が2,000円以下に収まる最大寄附額を1,000円単位で算出 | Must |
| FR-11 | 控除内訳の可視化 | 寄附額に対する「所得税軽減／住民税基本分／住民税特例分／自己負担」の内訳を積み上げグラフで表示 | Must |
| FR-12 | 自己負担曲線 | 寄附額を横軸に、自己負担額を縦軸に取ったグラフ。上限を超えた先の増え方が一目で分かる | Should |
| FR-13 | 安全率設定 | 収入見込みの不確実性に対し、上限額に安全率（既定90%）を掛けた「推奨額」を提示。安全率は変更可 | Must |
| FR-14 | 申告方式の判定・警告 | 医療費控除等の入力がある場合、「確定申告が必要 → ワンストップ特例は無効」を明示警告。ワンストップ特例と確定申告の結果比較 | Must |
| FR-15 | 警告エンジン | 下記の条件を検知して警告（§6.2） | Must |
| FR-16 | シナリオ比較 | 「復職月」「賞与額」「医療費」「寄附額」を変えた複数シナリオを並列比較 | Should |
| FR-17 | 検算モード | 源泉徴収票・住民税決定通知書の実績値を入力し、計算エンジンの出力との差分を表示（エンジンの信頼性検証用） | Should |
| FR-18 | 根拠の開示 | 各計算ステップの中間値（給与所得控除額、課税総所得、限界税率、所得割額…）を常時表示。「なぜこの上限になったか」を追跡可能にする | Must |
| FR-19 | 税制パラメータの外部化 | 税率表・控除額を年分ごとのJSONで管理し、UIから編集・追加可能にする | Must |
| FR-20 | 結果出力 | 計算結果のPDF/印刷出力 | Should |
| FR-21 | 寄附実績の記録 | 実際に寄附した自治体・金額・日付を記録し、残枠を表示。ワンストップ特例申請の要否・締切管理 | Could |
| FR-22 | 複数年最適化 | 「今年寄附する vs 来年に回す」の比較。育休のように年をまたいで所得が変動する場合の配分提案 | Could |
| **FR-23** | **人物プロファイル管理** | 人物の追加・リネーム・削除・切替。人物ごとに識別色を設定。表示名は任意文字列とし、**本名の入力を強制しない**（既定は「本人」「配偶者」等） | Must |
| **FR-24** | **ブラウザ永続化** | 全データをIndexedDBに保存。`navigator.storage.persist()` で永続化許可を要求し、ストレージ退避（eviction）を抑止する。保存状態と使用容量を設定画面に表示 | Must |
| **FR-25** | **エクスポート** | 全データまたは選択した人物のみをJSONファイルとして書き出す。`schemaVersion` を含めること。ファイル名は `taxsim-{人物}-{YYYYMMDD}.json` | Must |
| **FR-26** | **インポート** | エクスポートJSONを読み込む。**上書き／マージ／新規人物として追加** の3モードを選択でき、実行前に差分プレビューを表示する。スキーマ移行（旧バージョン→現行）を自動適用 | Must |
| **FR-27** | **暗号化エクスポート** | パスフレーズを指定した場合、Web Crypto API（AES-GCM + PBKDF2）でエクスポートJSONを暗号化する。クラウドドライブ等にバックアップを置く場合を想定。§2.4 の制約を明記する | Should |
| **FR-28** | **バックアップ督促** | 最終エクスポートから30日以上、またはデータ更新から一定回数エクスポートしていない場合に、ダッシュボードでバックアップを促す。ブラウザデータ消去による喪失リスクを明示 | Must |
| **FR-29** | **世帯ビュー** | 複数人物の上限額・推奨額を並べ、世帯合計を表示。配偶者の合計所得金額を、配偶者控除判定のために本人プロファイルへ参照連携する | Should |
| **FR-30** | **初回オンボーディング** | 初回アクセス時に「データはこのブラウザにのみ保存され、外部送信されない」「ブラウザのデータを消すと失われる」ことを説明し、人物プロファイルを1件作成させる | Must |
| **FR-31** | **全データ削除** | 設定画面から全データをワンクリックで削除できる（共有端末での利用後を想定）。確認ダイアログ必須 | Must |

### 6.2 警告エンジンの検知条件（FR-15）

| ID | 条件 | メッセージ趣旨 |
|---|---|---|
| W-01 | 差引所得税額が0円 | 住宅ローン控除で所得税がゼロのため、寄附金控除の所得税分の効果が発生しない。自己負担が2,000円を超える |
| W-02 | 住宅ローン控除の切り捨て損失 > 0 | 住宅ローン控除を使い切れていない。寄附額を増やすと損失が拡大する可能性 |
| W-03 | 寄附により切り捨て損失が増加 | 寄附金控除で所得税が減った結果、住宅ローン控除の切り捨てが増える。実質的な上限はこれを織り込んだ額 |
| W-04 | 医療費控除等があるのにワンストップ特例を選択 | 確定申告するとワンストップ特例申請は全て無効になる |
| W-05 | 所得割額が0円（非課税） | ふるさと納税による控除が受けられない |
| W-06 | 収入見込みの確定率 < 50% | 実績月が少ない。安全率を高め、年末に再計算することを推奨 |
| W-07 | 特例分が20%枠に到達 | 上限額に到達している。これ以上は全額自己負担 |
| W-08 | 年末調整で住宅ローン控除を受けている | 確定申告時は住宅ローン控除も申告し直す必要がある |

## 7. 非機能要件

| ID | 分類 | 要件 |
|---|---|---|
| NFR-01 | プライバシー | **入力データ（所得・控除・人物情報）を外部に送信しない**。完全クライアントサイドで動作し、入力値がネットワークに出ることが一切ないこと。禁止するのは「データを送る通信」であり、**Webフォント・CDN等の静的アセットを取得する通信は許可する**（§7.1 参照） |
| NFR-15 | 外部アセット | Google Fonts・CDN を利用してよい。ただし ①オフライン動作を壊さないこと（Service Worker でキャッシュする） ②CDN 障害時にアプリが起動不能にならないこと ③外部スクリプトには SRI（Subresource Integrity）を付すこと |
| NFR-02 | 永続化 | IndexedDB に保存（設定のみ localStorage）。バックアップはJSONファイルとして手動エクスポート。Storage Persistence API により退避を抑止 |
| NFR-03 | 可搬性 | PWAとしてインストール可能。オフライン動作。デバイス間の移行はエクスポートJSONによる |
| NFR-10 | 配信 | **GitHub Pages で静的配信可能であること**。ビルド成果物が静的ファイルのみで完結し、サーバーサイドのランタイム・環境変数・シークレットを一切必要としない |
| NFR-11 | サブパス対応 | `https://<user>.github.io/<repo>/` のようなサブパス配信で正しく動作すること（アセットパス・ルーティング・PWAスコープ） |
| NFR-12 | データ分離 | 同一ブラウザ内の人物プロファイル間でデータが混線しないこと。人物削除時に該当データが完全に消えること |
| NFR-13 | 互換性 | エクスポートJSONに `schemaVersion` を持たせ、旧バージョンのファイルを現行スキーマへ自動移行できること。移行不能な場合は明示的にエラーとし、黙って破損させない |
| NFR-14 | 更新配信 | Service Worker のキャッシュ更新時に、税制パラメータの古い版が残らないこと。新バージョン検知時に再読み込みを促す |
| NFR-04 | 正確性 | 金額は整数（円）で扱い、浮動小数点誤差を排除。端数処理（切捨/四捨五入）は税法の規定に忠実に実装 |
| NFR-05 | 保守性 | 税制パラメータをコードから分離。年度が変わったらJSONの追加のみで対応可能 |
| NFR-06 | 検証可能性 | 計算エンジンは副作用のない純粋関数群として実装し、単体テストでカバー率80%以上。国税庁の計算例・自身の過年度実績をテストケース化 |
| NFR-07 | 応答性 | 二分探索を含む再計算が100ms以内（入力変更に対しリアルタイム再計算） |
| NFR-08 | 対応環境 | 最新版のChrome / Safari（デスクトップ・モバイル） |
| NFR-09 | 免責表示 | 全画面で「概算であり、最終確認は税務署・税理士へ」の旨を表示 |

### 7.1 外部通信の可否（NFR-01 の具体化）

守るべき本質は「**入力した所得情報が外部に出ないこと**」であり、「外部と一切通信しないこと」ではない。両者を混同すると、フォントすら使えない過剰な制約になる。基準は次のとおり。

| 区分 | 可否 | 例 |
|---|---|---|
| **静的アセットの取得** | ✅ 許可 | Google Fonts、jsDelivr / unpkg 等からのライブラリ配信、アイコンフォント |
| **アプリからの能動的なデータ送信** | ❌ 禁止 | 入力値を含むフォーム送信、外部APIへの計算依頼 |
| **アナリティクス** | ⚠️ 条件付き | ページビュー等の集計は可。ただし**入力値・画面上の金額をイベントパラメータに含めない**こと。導入する場合はプライバシーポリシーに明記 |
| **エラー収集（Sentry等）** | ⚠️ 条件付き | 導入する場合、スタックトレースに所得情報が載りうる（変数のキャプチャ、Breadcrumb のDOM記録）。`beforeSend` でのスクラビングを必須とし、既定の自動キャプチャを無効化する。**難しければ導入しないほうが安全** |
| **外部への自動バックアップ** | ❌ 禁止 | クラウド同期は非目標（§2.3）。バックアップは手動エクスポートのみ |

副次的な留意点として、Google Fonts や CDN を使うと**利用者のIPアドレスとリファラが第三者に渡る**。所得情報が漏れるわけではないが、公開アプリとして README に一行記載しておくとよい。気になる場合は `@fontsource/*` 等でフォントをセルフホストする選択肢もあり、その場合はオフライン対応も自動的に解決する。

## 8. 制約・前提

| ID | 内容 |
|---|---|
| C-01 | 税制は毎年改正される。特に令和7年度・令和8年度改正で基礎控除・給与所得控除が大きく動いており、2025年分と2026年分で計算パラメータが異なる（仕様書 §3 参照） |
| C-02 | 令和8年度改正は令和8年12月1日施行・令和8年分以後の所得税に適用。月次源泉徴収への反映は令和9年1月以降のため、2026年は「源泉徴収は旧税額表・年末調整で精算」となる。手取りベースの見込みと税額ベースの計算がずれる点に注意 |
| C-03 | 個人住民税の控除額改正は所得税と適用時期がずれる。パラメータは年度ごとに独立して管理する |
| C-04 | 自治体独自の超過課税（神奈川県の水源環境保全税による県民税所得割0.025%上乗せ、横浜市のみどり税による均等割上乗せ等）は継続・改廃があるため要確認項目とする |
| C-05 | ふるさと納税制度自体の変更（2025年10月のポイント付与禁止等）は返礼品の実質価値に影響するが、税額計算には影響しない |
| C-06 | 育児休業給付金は雇用保険法の規定により非課税。社会保険料も免除されるため、社会保険料控除は発生しない |

## 9. リスクと対応

| ID | リスク | 影響 | 対応 |
|---|---|---|---|
| R-01 | 税制パラメータの誤り | 上限額を誤り、自己負担が増える | パラメータJSONに出典URLと確認日を必須項目として持たせる。起動時に「最終確認日から1年以上経過」を警告 |
| R-02 | 2026年の収入見込み誤差 | 上限を過大評価 | 安全率の既定を90%とし、年末（11〜12月）の再計算をリマインド |
| R-03 | 「所得割額の20%枠に住宅ローン控除が影響するか」の解釈差 | 上限が数千円ずれる | 両解釈での計算結果を併記できるようにし、保守的な方（低い方）を既定の推奨値とする |
| R-04 | 賞与の減額 | 見込み過大 | 賞与を独立した入力項目とし、査定期間に育休が含まれる場合の減額率を設定可能にする |
| R-05 | 実装バグ | 誤った意思決定 | 検算モード（FR-17）で過年度実績と突き合わせてから本番利用する運用とする |
| **R-06** | **ブラウザデータの消失** | 入力した全データを喪失 | 最大のリスク。ブラウザの「閲覧データを削除」、シークレットウィンドウでの利用、iOS Safari の未訪問サイトのストレージ削除、OS再インストール等で消える。`navigator.storage.persist()` の要求（FR-24）＋バックアップ督促（FR-28）＋オンボーディングでの明示（FR-30）の3段構えで緩和する。**技術的に完全な防止は不可能なため、「消えうる前提でエクスポートを促す」設計とする** |
| **R-07** | **共有端末での他人の閲覧** | 所得情報の漏洩 | 静的配信では真のアクセス制御を実装できない。暗号化エクスポート（FR-27）と全データ削除（FR-31）で緩和し、制約を明示する |
| **R-08** | **エクスポートJSONの取り扱い** | 平文の所得情報がクラウド等に置かれる | エクスポート時に「所得情報を含む平文ファイルである」旨を警告し、暗号化オプションを提示する |
| **R-09** | **公開アプリとしての誤用** | 第三者が概算値を鵜呑みにする | 全画面に免責を表示。README にも「個人利用のための概算ツールであり税務助言ではない」旨を明記 |
| **R-10** | **Service Worker のキャッシュ固着** | 古い税制パラメータで計算される | パラメータJSONにバージョンを持たせ、SW更新時に強制再取得。アプリ内に「パラメータ最終確認日」を常時表示（R-01と併せて運用） |

## 10. リリース計画

| フェーズ | 内容 | 目安 |
|---|---|---|
| **Phase 0**（土台） | GitHub Pages へのデプロイパイプライン、IndexedDB永続化、人物プロファイル、エクスポート／インポート、オンボーディング。FR-23〜26, 28, 30, 31 | 空の画面でもよいので先にデプロイと保存を通す |
| **Phase 1**（MVP） | 計算エンジン（所得税・住民税・住宅ローン控除・上限額算出）＋単一年入力フォーム＋結果表示。FR-01〜11, 13, 14, 15, 18, 19 | ここまでで当面の課題は解決する |
| **Phase 2** | 可視化強化、シナリオ比較、検算モード、世帯ビュー、暗号化エクスポート。FR-12, 16, 17, 20, 27, 29 | |
| **Phase 3** | 寄附実績管理、複数年最適化、PWA化。FR-21, 22 | |

**Phase 0 を先に置く理由**: 永続化と人物レイヤーはデータモデルの根幹に関わるため、計算エンジンを作り込んだ後から差し込むと全体の書き直しになる。一方でデプロイは早いほど「実機で動く」確認が早く取れる。

**Phase 1 を最優先とする理由**: 本件の課題は「今年の上限額が分からない」ことに尽きる。UIの作り込みより、計算エンジンの正確性と根拠開示（FR-18）に投資すべき。
